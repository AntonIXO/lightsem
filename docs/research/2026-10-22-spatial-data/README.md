RPMC-L2 describes video-to-light label generation and its public dataset format
as HSV/value lighting data. The Roskilde repository describes lighting feature
vectors and audio features and states that additional data were not published
because of copyright restrictions. LightingGen reports a virtual-stage DMX
dataset, but the dataset itself was not found in a public repository during
this review. None of these sources should be treated as captured venue DMX
with calibrated fixture geometry.

## What LightSem already produces

The active body-transfer path produces, before DMX encoding:

- targets[T,N,3]: spatial target points for each beam/laser and fixed bulb positions;
- source_points[T,N,3]: the body attachment point used for moving outputs;
- dimmer[T,N] and bulb field centers;
- an explicit output patch with positions, body region, attachment weights,
  pan/tilt ranges and simulated fixture roles.

The compiler can decode emitted 16-bit pan/tilt and diagnostics can compare
requested rays with emitted rays. The current selected configuration deliberately
sets apply_motion_limits: false; a good render under that setting is therefore
a visual preview of unbounded requested targets, not proof of motor feasibility.
The baseline C motion model and P2 color model remain unchanged.

## What is needed for a real-fixture check

For each actual fixture personality and venue patch, record:

1. pan/tilt physical travel and zero orientation (including inversion/swap);
2. maximum speed and acceleration for the selected mode and any mode-dependent limits;
3. control resolution, update rate, latency and whether the console applies its own slew/curve;
4. fixture position and aim in one stage coordinate system;
5. shutter/strobe/zoom limits separately from movement;
6. the exact emitted DMX/Art-Net stream and the decoder/profile version.

Then audit the decoded emitted trajectory, not only the body targets:

- finite values and channel ranges;
- angular position within travel;
- component speed and acceleration from successive decoded frames;
- 3D ray-direction error and requested-to-emitted lag;
- duplicate or inactive outputs;
- timestamps, frame rate and any console interpolation.

A calibrated venue capture or manufacturer GDTF/fixture personality plus a
known patch is the realistic next source. Until one is available, the
synthetic benchmark below is an engineering regression fixture, not training
data and not a substitute for hardware validation.

## Reproducible synthetic control set

Generate the tiny deterministic set with:

    python tools/synthetic_spatial_controls.py --out-dir data/synthetic/spatial_controls_v1
    pytest -q tests/test_synthetic_spatial_controls.py

requested_fast_deg is intentionally inadmissible. feasible_projected_deg is
passed through a deterministic second-order position/velocity projector and
must satisfy the declared bounds, speed and acceleration limits. MANIFEST.json
labels the origin and states that the files contain neither original DMX nor
video-extracted paths. The generated NPZ is not checked into the repository;
regenerate it from the script when needed.

## Recommended data acquisition order

1. Ask LightingGen authors for the raw virtual-stage DMX, fixture profile,
   positions, limits, coordinate frame and license. Accept it only with a
   manifest that distinguishes requested commands from simulator-emitted commands.
2. If unavailable, create a small licensed virtual rig in Blender/GDTF or Capture/Depence/QLC+ and export both the command stream and fixture metadata.
3. For a hardware check, replay the same stream through the actual console or Art-Net/DMX interface, capture output and compare decoded positions against the declared limits.
4. Keep RPMC-L2 and Cross-Modal Metrics as color/timing and evaluation references, never as spatial DMX supervision.

This document records a source decision; it does not authorize model training.
